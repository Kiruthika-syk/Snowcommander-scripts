Snow Commander

Automated deployment, validation and teardown of enterprise security tooling across Red Hat Enterprise Linux estates — from a vSphere template to a verified host, with every step logged.

CrowdStrike Falcon 8.10.0-19402 · Tanium Client 7.8.4.1298 · EL7–EL10 · x86_64 + aarch64

Overview

Snow Commander installs and verifies five security components on RHEL-family servers. It grew out of a single installer script and now has four layers that share the same core logic: a host-side orchestrator, an SSH fan-out control plane, a container image, and a CI/CD pipeline.

Host orchestrator

security.sh runs on the target. Detects the platform, picks and validates packages, installs, reports.

Control plane

deploy_targets.sh fans out over SSH to many hosts with bounded concurrency and retries.

Container

AlmaLinux 9 image carrying the scripts and all 14 packages. Orchestrates outward; runs no agent itself.

Validation harness

e2e_validate.sh builds a VM from a template, installs, verifies, uninstalls, confirms.

What it does

  • Detects the platform from /etc/os-release and maps RHEL, CentOS, Rocky, AlmaLinux and Oracle Linux onto an elN tag.
  • Selects the right package out of 14 staged RPMs based on that tag and the architecture. No version is hardcoded.
  • Validates before installing — header parse, name match, architecture fit and payload digest verification.
  • Installs idempotently. Re-running reports UNCHANGED rather than reinstalling or bouncing a healthy service.
  • Never blindly overwrites. Existing config is backed up to <file>.sectools-bak.<timestamp> first.
  • Reports per host and per component so one failure never masks another.
  • Redacts secrets from stdout and logs while keeping installation status fully visible.
Why digest validation matters. A staged Falcon RPM was 3.8 MB against a declared 155 MB payload — a truncated download that would have failed mid-install with a confusing error. rpm -K catches it before the host is touched.

Why the agents are not containerized

The container orchestrates; it never hosts an agent. Each of these is bound to its host, and a containerized copy would report the container instead of the VM:

CrowdStrike FalconKernel / eBPF sensor, host-unique agent ID
Tanium ClientHost systemd, hardware and patch inventory

End-to-end flow

The validation harness runs eight stages and prints a pass/fail matrix at the end.

  1. Connect to vSpherepyVmomi SmartConnect to vCenter on 443.
  2. Find the templateSearch restricted to SnowCommander/Templates. Anything outside is invisible and refused with exit 7.
  3. Template → VMClone (template preserved), connect the NIC at both connected and startConnected, power on, wait for an IPv4 address.
  4. Place the scriptsRemove the stale 2026snowcommander payload, build a matched 88 MB bundle, extract to /home/tpx-admin/2026snowcommander, and add the FQDN to /etc/hosts. Secrets follow on a separate channel into a 0600 file.
  5. Install the toolsRHSM register if needed, then security.sh all — detect, select, validate, install, configure.
  6. Verify with systemctlsystemctl is-active per service, rpm -q per package, plus structured verification.
  7. Uninstall the toolsRemove the three agents — Tanium, CrowdStrike and Sentinel. The cmdbsync account and the Red Hat subscription are deliberately retained, and stage 7 re-checks both to prove they survived. Appliance templates unregister from RHSM here.
  8. Confirm the scripts remainAssert every expected script is still present, then shred securitytools.env.

With --template-cycle a ninth step follows: shut the guest down cleanly and call MarkAsTemplate, so the validated machine becomes a golden image again.

Failure is self-healing. If the run ends before finalisation, an EXIT trap converts the object back to a template anyway. A crash between stage 3 and the end cannot leave your golden image stranded as a VM.

Mechanism

Platform detection

Reads ID and VERSION_ID from /etc/os-release, maps the family to an elN tag, and normalises the architecture. Debian, Ubuntu and Fedora are rejected with exit 3 and an explicit message rather than being silently mis-served — no .deb packages exist here.

Names lie, metadata doesn't. The template BLR-GI-6.6 is Vocera 6.6 running on RHEL 7.9, not RHEL 6.6. Detection reads the OS, never the label.

Idempotency

Every component compares desired state against actual state:

  • CrowdStrike — skips entirely when build, CID and service state all match. CID compared as bare 32 hex characters, since falconctl reports it lowercase and without the checksum suffix.
  • Tanium — restarts only if the RPM or tanium-init.dat actually changed.
  • cmdbsync — never resets an existing account's password unless CMDBSYNC_FORCE_PASSWORD=1.
  • Sentinel — skipped when already Connected to the intended subscription, because sentinel_core.sh disconnects before reconnecting.
  • syslog — writes only on content change, validates with rsyslogd -N1, rolls back on failure.

Secret handling

Secrets are never baked into an image, written to a tarball, or passed as command arguments where ps could read them. They travel on a dedicated SSH channel into a 0600 file and are shredded afterwards. A sed filter in the output pipeline masks secret values everywhere they appear — including in output from dnf, falconctl and azcmagent, which these scripts do not control. Installation status is never hidden. The CID is deliberately not redacted: it is an identifier, not a credential.

Package selection

14 RPMs staged; exactly two are shipped per host. Selection is by glob with the highest version winning, so staging a newer sensor needs no code change.

TargetCrowdStrikeTanium
el7 x86_64✓✓
el7 aarch64not published✓ via arch match
el8 / el9 / el10 x86_64✓✓
el8 / el9 / el10 aarch64✓✓
Tanium is arch-keyed, not version-keyed. The seven Tanium filenames contain only two unique payloads — one glibc2.17 x86_64 build and one glibc2.26 aarch64 build. The rheN in the filename is cosmetic, so selection falls back to matching the RPM header's architecture.

Validation gate

Every candidate must pass all five checks or the run aborts before the host is modified: file present and non-empty, header parseable, package name matches, architecture installable, payload digests verify.

Red Hat subscriptions

rsyslog installs from Red Hat repositories, so an unregistered RHEL host cannot complete the syslog component. --rhsm-mode auto (the default) decides from the template name:

TemplateBehaviour
*Redhat*Register, install, verify — stays registered
*GI*, *Engage*Register, install, verify — unregisters after stage 6
anything elseSkipped; override with --rhsm-mode keep|remove

Repository names are derived per version, not hardcoded:

Execution — from your VM

The harness runs on the jump VM because it needs pyvmomi and sshpass. The container is the right tool for production fleet deploys over key auth.

# 0. Prepare — once per shell
cd /home/tpx-admin/snowcommander_scripts
set -a; source ~/.snowcommander-creds.env; set +a

# 1. Prove credentials and scope. Read-only, changes nothing.
#    Prints each template's REAL guest OS.
python3 scripts/vsphere_provision.py \
  --vcenter blr-vsphere-01.strykercorp.com \
  --list-templates --insecure

# 2. Dry run against a host you already have — no VM is created
./scripts/e2e_validate.sh --existing-host blr-gi-6 --keep-tools

One template at a time

Two ways to validate a template. Pick based on whether you want a second object in the inventory afterwards.

Round trip on the template itself (recommended)

No new VM. The template becomes a VM, is validated, and is converted back.

cd /home/tpx-admin/snowcommander_scripts
set -a; source ~/.snowcommander-creds.env; set +a

./scripts/e2e_validate.sh \
  --vcenter fw-vsphere-01.strykercorp.com \
  --template FW-Redhat-9 \
  --template-cycle \
  --portgroup 'fwa-vlan106' \
  --fqdn-domain vcraeng.com \
  --insecure

--template-cycle is shorthand for --mode convert, the destructive acknowledgement, and --convert-to-template.

Clone into a new VM

Leaves the template untouched and produces a second object.

./scripts/e2e_validate.sh \
  --vcenter fw-vsphere-01.strykercorp.com \
  --template FW-Redhat-9 \
  --name e2e-fw-rhel9 \
  --portgroup 'fwa-vlan106' \
  --insecure

Useful variations

# keep the tools installed for inspection (skip stage 7)
./scripts/e2e_validate.sh ... --keep-tools

# force subscription behaviour instead of inferring it from the name
./scripts/e2e_validate.sh ... --rhsm-mode remove

# install only some components
./scripts/e2e_validate.sh ... --components "crowdstrike tanium"

# change what stage 7 tears down (default: the three agents)
./scripts/e2e_validate.sh ... --uninstall-components "tanium crowdstrike"

# different script location on the target
./scripts/e2e_validate.sh ... --remote-dir /opt/snowcommander

# validate a host that already exists, skipping stages 1-3
./scripts/e2e_validate.sh --existing-host blr-gi-6 --keep-tools
No guest customization is applied. The VM boots with the template's own hostname and static IP. Two clones of the same template must never run at once, and the address must be free before you start.

Every template in one vSphere

cd /home/tpx-admin/snowcommander_scripts
set -a; source ~/.snowcommander-creds.env; set +a

VC=fw-vsphere-01.strykercorp.com

All three vSphere at once

Each vCenter is processed in its own background job, with one log file per template. wait blocks until every site finishes, then a combined summary is printed.

cd /home/tpx-admin/snowcommander_scripts
set -a; source ~/.snowcommander-creds.env; set +a

mkdir -p /tmp/e2e-runs

run_site() {
  local vc="$1" site="$2" pg="$3"; shift 3
  for t in "$@"; do
    ./scripts/e2e_validate.sh \
      --vcenter "$vc" --template "$t" \
      --name "e2e-${site}-${t,,}" \
      --portgroup "$pg" --insecure \
      > "/tmp/e2e-runs/${site}-${t}.log" 2>&1
    echo "${site} ${t} exit=$?" >> /tmp/e2e-runs/summary.txt
  done
}

: > /tmp/e2e-runs/summary.txt

run_site blr-vsphere-01.strykercorp.com blr 'VM Network' BLR-Redhat-9 BLR-Redhat-10 BLR-GI-6.6 &
run_site fw-vsphere-01.strykercorp.com  fw  'VM Network' BLR-Redhat-9 BLR-GI-7.1 &
run_site stc-vsphere-01.strykercorp.com stc 'VM Network' BLR-Redhat-9 BLR-GI-7.2 &

wait
echo "=== combined summary ==="
column -t /tmp/e2e-runs/summary.txt
Run one template end to end first. Parallel runs across three sites create real VMs simultaneously. Confirm a single clean pass before scaling out.

Fleet deploy — existing servers

For servers that already exist, skip vSphere entirely and use the container.

# Build once
cd /home/tpx-admin/snowcommander_scripts
podman build -t snowcommander-deployer:latest .

# Inventory: one hostname per line
cp inventory.example inventory && vi inventory

# plan (read-only) → verify → deploy
podman run --rm \
  --env-file ~/.snowcommander-creds.env \
  -v ./secrets/ssh_key:/run/secrets/ssh_key:ro \
  -v ./secrets/known_hosts:/run/secrets/known_hosts:ro \
  -v ./inventory:/etc/snowcommander/inventory:ro \
  -e INVENTORY=/etc/snowcommander/inventory \
  -e PARALLEL=10 -e RETRIES=2 \
  snowcommander-deployer:latest plan

Swap the final argument for verify or deploy all. Or run the fan-out directly on the VM:

./scripts/deploy_targets.sh --inventory ./inventory --mode plan --parallel 10
./scripts/deploy_targets.sh --hosts host1,host2 --mode deploy --components all --retries 2

Why nginx and not Tomcat

Tomcat is a Java servlet container. There are no servlets, JSPs or Java here — it is one HTML file — so Tomcat would add a JVM and a considerably larger attack surface for no functional gain. The nginx:alpine image is a few megabytes and serves static content directly.
